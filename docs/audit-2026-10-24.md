# Code and runtime audit — 24 October 2026

## Initial findings (before fixes)

| Priority | Finding | Evidence / trigger | Required correction |
| --- | --- | --- | --- |
| High | Backup JSON depends on runtime field names | `Backup.kt` enumerates `declaredFields`; release enables R8 without entity field keep rules. Field renaming can break the fixed restore keys. | Explicit versioned JSON field names; preserve formats 1 and 2. |
| High | Restore accepts multiple transactions for one SMS | Validation checks entry IDs but not uniqueness of non-null `smsKey`. A modified, validly encrypted backup can double-count a message. | Reject duplicate SMS associations before replacing any data. |
| Medium | Stale delete overwrites later corrections | `delete(entry)` upserts the caller's entire snapshot. A category/amount correction after that snapshot is lost. | Read current data under the repository lock and mark only that entry deleted. |
| Medium | Stale Inbox dismissal overwrites saved state | `dismiss(message)` upserts the caller's REVIEW snapshot even after ingestion has saved it. | Serialize dismissal and act only on a currently reviewed message. |
| Medium | Failed SMS query can advance reconciliation cursor | A null provider cursor is treated as an empty successful scan. | Treat unavailable provider results as failure and retain the cursor. |
| Medium | SMS receiver cleanup can be skipped | WorkManager enqueue precedes `pending.finish()` in the same finally block; an enqueue failure skips completion. Receiver/worker also swallow coroutine cancellation. | Unconditional completion, cancellation propagation, private diagnostic events. |
| Low | Repeated invariant queries during ingestion | Accounts and trusted senders are reloaded for every candidate; rules for every saved message. | Cache invariant configuration within each database transaction. |
| Low | Unused widget resources | Lint and source/test/resource reference searches find three unused strings and an unused day/night color. | Remove only proven unused resources. |

## Security and static review observations

- The merged release manifest declares no INTERNET permission, disables automatic backups, and excludes app data from cloud backup/device transfer. The SMS receiver requires BROADCAST_SMS. Exported WorkManager/ProfileInstaller components require privileged platform permissions; widgets and the startup provider are not exported. Launcher routing opens local UI and does not perform financial writes.
- Notification pending intents are explicit and immutable, with distinct entry URIs. Reminder text contains no financial values. Deletion now cancels its reminder after the transaction.
- Backup uses PBKDF2-HMAC-SHA256 (600,000 iterations), fresh random salt/nonce and authenticated AES-GCM. Existing wrong-password/tamper tests remain relevant; restore parses/validates before replacement. No schema or backup format bump is required by these fixes.
- A minified release's mapping confirms entity fields are renamed (for example Account's `id` becomes `a`). Explicit JSON keys remove this dependency; Android documents the general [reflection/R8 limitation](https://developer.android.com/topic/performance/app-optimization/keep-rules-overview).
- Checked the upstream [AndroidX](https://github.com/androidx/androidx/security/advisories) and [Haze](https://github.com/chrisbanes/haze/security/advisories) public advisory pages on 24 October 2026: neither listed published advisories. This is a limited upstream check, not a complete transitive dependency vulnerability scan or proof of absence. No dependencies were changed by this audit.
- Reviewed parser identity compatibility, transactions, transfer matching, Room migrations, reports, navigation/drafts, shared transitions, header/gesture ownership, adaptive panes, widget calculations, lifecycle observers and benchmark isolation. No redesign or schema change was introduced. A declaration/reference scan found no further proven dead application functions; framework overrides and compatibility paths were retained.
- Existing ignored logs only show successful visual capture tests at font scales 1.0 and 2.0, not application crash/ANR or performance evidence. They do not establish current runtime health.

## Remaining risks and follow-up

1. **Startup responsiveness:** investigate the reproduced debug startup warning with a bounded main-thread/FrameTimeline trace and compare a representative release build before making further performance changes. Cold/warm startup and device scheduling need separate measurement.
2. **Large-ledger scaling:** ingestion still loads full entry/message lists, and transfer matching scans candidates repeatedly. Inbox/account presentation also contains remembered list scans. Their cost at large history sizes was not measured; index transfer candidates and move additional scans off-thread only with representative synthetic evidence and regression coverage.
3. **Extreme aggregate money ranges:** individual money parsing rejects overflow, but report/balance `Long` sums have no ledger-wide aggregate range guard. Values near the storage limit can wrap when combined. A follow-up should define supported aggregate limits and surface checked-arithmetic failures consistently across reports, widgets, imports and editors; silently clamping totals is inappropriate.
4. **Recovery/session races:** provider failure now preserves the scan boundary, but capture disable/re-enable or restore during an already-running provider scan merits a deterministic interleaving test. No session-generation mechanism was introduced in this audit.
5. **Coverage gaps:** OS-delivered live SMS, notification permission grant/denial and reminder taps, provider-null failure injection, receiver scheduling failure injection, process death during restore, v1→v3 on-device migration, minified backup round-trip on-device, TalkBack, foldable/landscape/keyboard combinations, Doze/reboot recovery and sustained memory/power behavior were not exercised in this run. Screenshot capture was not enabled and no new visual acceptance is claimed.

The original app/benchmark UIAutomator dependency changes were preserved. No commit, personal update installation, benchmark run or performance certification was performed.

## Follow-up status (later on 24 October 2026)

A second hardening pass addressed several items above. These results come from the JVM tests, lint and an isolated device run (55 of 56 device tests; the optional `VisualReviewTest` is skipped), not from new measurements.

1. **Startup responsiveness:** not investigated; still open.
2. **Large-ledger scaling:** partly addressed. Ingest and transfer matching use targeted queries and a join by reference, `monthlySummary` runs in one pass, and widgets collect only the current month. Cost at large history sizes is still unmeasured.
3. **Aggregate money ranges:** still open; no ledger-wide checked arithmetic was added.
4. **Recovery/session races:** the reconcile cursor update now runs under the repository mutex, so it cannot overwrite a restore; a deterministic interleaving test does not exist.
5. **Coverage gaps:** v1 to v4 migration is now tested on a device. Restore validation, backup header formats and SMS identity have JVM tests. The minified-release backup round trip is documented in `docs/development.md` but has not been run. Live OS-delivered SMS, notification permission flows, TalkBack, keyboard, foldable and Doze/reboot checks remain unexercised, and the 200% widget and landscape-style automation was removed.

Other changes since this audit: backup header `PKTLGR02`, Room schema 4 with SMS body purging, a lint baseline, release shrinking with explicit R8 rules, and the widget rework. See `docs/architecture.md` (Recent behavior changes) for details.
